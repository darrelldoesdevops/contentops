## Summary

The codebase has three distinct positioning bugs that cause content to overlap TikTok's UI chrome. The overlay title's left starting position (`scale(30)` = 30px) places the orange accent bar at x=18px, which clips under TikTok's device bezel/UI and explains the "left edge clipped" report. The ASS subtitle `MarginR=40` allows text to extend to x=1040 of the 1080px frame, overlapping TikTok's 120px-wide right icon column (like/comment/share). Long title lines generated by Claude can also exceed the safe zone width at font_size=144.

The video output resolution fix requires adding `scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920` to the pipeline. The pipeline currently has no resize step — normalize uses `-c:v copy`, cut re-encodes but doesn't resize. Adding a dedicated scale stage before normalize is the cleanest approach. iPhone portrait video is close to 9:16, so cropping will be minimal.

**Primary recommendation:** Fix three constants in two files (`overlay.rs`, `caption.rs`), add a Rust word-wrap function, add a `scale_to_tiktok()` helper in `ffmpeg.rs`, and define named safe zone constants in a new `src/tiktok.rs` module shared by both files.

### Pattern 1: Scale-to-Fill with Center Crop

**What:** Scale video so smaller dimension equals target, then center-crop to exact target size
**When to use:** Source aspect ratio != target (no black bars allowed)

```
// ffmpeg filter string
"scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920"
```

This filter chain: (1) scales up so both dimensions are >= target while preserving AR, (2) center-crops to exact 1080x1920. For iPhone portrait (already ~9:16), the crop is 0-minimal.

### Pattern 2: Named Safe Zone Constants Module

**What:** Single source of truth for TikTok UI dimensions
**When to use:** Any code that positions text or graphics in output video


### Pattern 3: Title Word-Wrap (No Font Library)

**What:** Pre-process multi-word title lines to stay within safe width using char-count estimate
**When to use:** Before passing lines to `build_title_filter()`

drawtext has no native max-width wrapping. The `fix_bounds` option only prevents clipping at frame edge, it doesn't rewrap text. Solution: Rust-side pre-processing.

```rust
// Impact font at fontsize f: condensed uppercase, ~0.5 * f average char width
// Space character: ~0.35 * f
// Conservative: estimate total width as char_count * (font_size as f64 * 0.55)
// This overestimates for narrow chars (I, l) but is safe for uppercase Impact

fn wrap_title_lines(text: &str, font_size: u32, safe_width: u32) -> Vec<String> {
    let avg_char_px = font_size as f64 * 0.55;
    let max_chars = (safe_width as f64 / avg_char_px).floor() as usize;

    let mut result = Vec::new();
    for input_line in text.split('\n') {
        let words: Vec<&str> = input_line.trim().split_whitespace().collect();
        let mut current_line = String::new();

        for word in words {
            let candidate = if current_line.is_empty() {
                word.to_string()
            } else {
                format!("{} {}", current_line, word)
            };

            if candidate.len() <= max_chars || current_line.is_empty() {
                current_line = candidate;
            } else {
                result.push(current_line.clone());
                current_line = word.to_string();
            }
        }
        if !current_line.is_empty() {
            result.push(current_line);
        }
    }
    result
}
```

Call this before `build_title_filter()` to normalize lines.

### Pattern 4: Overlay Left-Position Fix

**What:** Increase `final_x` reference constant in `overlay.rs` so text and accent bar clear the left safe margin
**Current:** `final_x = scale_i32(30, video_height)` → 30px → accent bar at x=18px (clips)
**Fix:** `final_x = scale_i32(80, video_height)` → 80px → accent bar at x=68px (clears 60px margin)

```rust
// overlay.rs
let final_x: i32 = scale_i32(80, video_height);  // was 30; left safe margin is 60px
let box_pad: u32 = scale(10, video_height);
let accent_w: u32 = scale(8, video_height);
let accent_x: i32 = final_x - accent_w as i32 - scale_i32(4, video_height);
// At 1920px: accent_x = 80 - 8 - 4 = 68px ✓ (clears 60px safe margin)
```

### Pattern 5: ASS MarginR Fix

**What:** Increase `MarginR` in ASS style so subtitle text doesn't extend into TikTok icon column
**Current:** `MarginR=40` → text extends to x=1040 (overlaps icon column at x=960)
**Fix:** `MarginR=120` → text clamped to x=960

ASS PlayResX/PlayResY are already 1080/1920 — no change needed there. Alignment=2 (bottom-center) is correct. MarginV=480 places text at y=1440 from top (480px from bottom), which clears the TikTok caption bar.

### Anti-Patterns to Avoid

- **Hardcoding pixel values inline:** Using literal `30`, `40`, `120` scattered through code instead of named constants; makes future safe zone changes require hunting through code
- **Using `fix_bounds=1` in drawtext as a substitute:** This clips text at frame edge, not at safe zone margin
- **Shrinking font instead of wrapping:** User explicitly chose wrapping over font-size reduction
- **Adding scale/crop in every stage:** Only need it once, before normalize; downstream stages inherit correct resolution

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Scale to fill without black bars | Custom aspect ratio math | `scale=W:H:force_original_aspect_ratio=increase,crop=W:H` | ffmpeg handles all edge cases including odd resolutions |
| Font glyph width measurement | Custom TTF parser | Char-count estimation with conservative multiplier | Accurate enough for wrapping; exact measurement would require `fontdue` or `rusttype` crate (not worth adding) |

**Key insight:** All geometric transforms are already in ffmpeg. The only custom logic needed is the Rust word-wrap pre-processor (because drawtext cannot auto-wrap with a width limit).

## Common Pitfalls

### Pitfall 1: Scale Filter + Crop Center vs. Top

**What goes wrong:** `crop=1080:1920` with default `x=(in_w-out_w)/2, y=(in_h-out_h)/2` center-crops. For talking-head video this is correct (face is centered). But if the user faces one side, cropping may cut them off.
**Why it happens:** Scale-to-fill always crops the longer dimension.
**How to avoid:** For iPhone portrait content (already close to 9:16), cropping is minimal (< 5% typically). No action needed.
**Warning signs:** Source video has aspect ratio far from 9:16 (e.g., landscape 16:9).

### Pitfall 2: Drawtext `text_w` Cannot Be Used for Wrapping

**What goes wrong:** Attempting to use `text_w` variable in a drawtext expression to limit width — this value is read-only output info, not a constraint parameter.
**Why it happens:** drawtext measures rendered text width but cannot split or reflow lines.
**How to avoid:** Always pre-process in Rust. Pass already-wrapped lines to `build_title_filter()`.
**Warning signs:** Trying to use `if(gt(text_w,...))` to conditionally change text — doesn't work.

### Pitfall 3: ASS MarginR Interpretation

**What goes wrong:** Thinking MarginR is distance from right edge of text, when it's the margin subtracted from the script-declared PlayResX.
**Why it happens:** The ASS spec says "MarginR = distance in pixels from the right-hand edge of the screen" for scripts using screen-relative positioning. With PlayResX=1080, text is rendered in the zone [MarginL .. PlayResX-MarginR].
**How to avoid:** With PlayResX=1080, MarginR=120 confines text to [40..960] x-range. Verify with `ffplay` + ASS preview.
**Warning signs:** Text still clips right side after increasing MarginR — could mean PlayResX/PlayResY mismatch with actual output resolution.

### Pitfall 4: Normalize Stage Uses `-c:v copy`

**What goes wrong:** Adding a `-vf scale=...` to normalize's pass 2 is incompatible with `-c:v copy` (stream copy cannot apply video filters).
**Why it happens:** normalize pass 2 copies video stream unchanged to avoid re-encode for audio-only changes.
**How to avoid:** Keep scale/crop as a SEPARATE ffmpeg call, not merged into normalize. Run it before normalize. If the source is already 1080x1920, skip the scale stage (probe dimensions first).
**Warning signs:** ffmpeg error "Filtering is not required, it can be replaced by direct stream copy."

### Pitfall 5: Scale Stage Adds Unnecessary Re-Encode

**What goes wrong:** Always running scale/crop even when source is already 1080x1920, adding encode time and quality loss.
**Why it happens:** ffmpeg filter always re-encodes.
**How to avoid:** Probe dimensions first with `probe_dimensions()`. Skip scale stage if `(w, h) == (1080, 1920)`.
**Warning signs:** Pipeline takes significantly longer for already-correct-resolution videos.

## Code Examples

### Scale-to-Fill 1080x1920

```rust
// ffmpeg.rs - add new function
pub fn scale_to_tiktok(input: &str, output: &str, verbose: bool) -> Result<FfmpegOutput, std::io::Error> {
    let vf = "scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920";
    let args = [
        "-i", input,
        "-vf", vf,
        "-c:v", "libx264",
        "-crf", "14",
        "-preset", "slow",
        "-pix_fmt", "yuv420p",
        "-c:a", "copy",
        output,
    ];
    if verbose { run_ffmpeg_verbose(&args) } else { run_ffmpeg(&args) }
}
```

## Open Questions

1. **MarginV: 480 -- increase or keep?**
   - What we know: 480px from bottom of 1920px frame; TikTok safe zone bottom is ~320-480px
   - What's unclear: "Subtitles are running into the overlay for TikTok" -- is this horizontal (right icons) or vertical (bottom bar)?
   - Recommendation: The right-icon overlap (MarginR=40) is the clear bug. Keep MarginV=480 as it's already conservative. If subtitles still obscure bottom UI after MarginR fix, increase to 520.

2. **Scale stage: skip when already 1080x1920?**
   - What we know: iPhone portrait is typically 1080x1920; probe_dimensions() is already available
   - What's unclear: Could source be 4K (3840x2160 landscape on iPhone)? Unlikely for portrait but possible
   - Recommendation: Always probe first; skip scale stage if dims == (1080, 1920) to avoid unnecessary re-encode.

3. **Title wrap char-count accuracy**
   - What we know: Impact is condensed, avg uppercase char ~55% of font_size; space ~35%
   - What's unclear: Very narrow chars (I, !, 1) and very wide chars (W, M) skew estimates
   - Recommendation: Use conservative 0.55 multiplier (slightly overestimates width → wraps slightly earlier than needed, which is safe). For the title use case this is acceptable.
